## D-1 음성인식: sherpa-onnx WASM + 한국어 Streaming Zipformer

> **재조사 (2026-11-26)**: 후보를 넓혔다. 주력은 KsponSpeech 학습 72M 스트리밍 Zipformer이고, 대안은 SenseVoice Small + VAD, Moonshine Tiny Korean + VAD, Chrome 온디바이스 Web Speech다. PoC에서 같은 데이터로 비교한다. 상세: [research/korean-stt-models.md](research/korean-stt-models.md)

1. **문제**: 메인오더가 말하는 동안 계속 인식해야 한다. 서버로 음성을 보내면 비용이 들고 "음성을 밖으로 보내지 않는다"는 원칙을 어긴다.
2. **대안**
   - Web Speech API: 쉽지만 Chrome은 음성을 구글 서버로 보낸다. 연속 인식이 일정 시간 뒤 끊기는 동작도 있어 30분 연속 실행에 별도 처리가 필요하다.
   - 클라우드 STT: 정확하지만 비용이 들고 MVP 제외 범위다.
   - Whisper 계열 WASM: 정확도는 좋지만 스트리밍이 아니라 구간 단위로 처리해 지연이 크고, 모델이 무겁다.
3. **가능해지는 것**: 서버 비용 없이, 음성을 밖으로 보내지 않고, 말이 끝나자마자 결과를 받는 스트리밍 인식.
4. **비용·한계**
   - 모델 파일이 크다. 공개된 커뮤니티 한국어 스트리밍 모델은 int8 기준 인코더 155MB, 디코더 5MB, 조이너 1MB 정도다 ([Hugging Face](https://huggingface.co/ken4869/lyr-asr-ko-streaming)). k2-fsa 공식 모델([sherpa-onnx-streaming-zipformer-korean-2024-06-16](https://huggingface.co/k2-fsa/sherpa-onnx-streaming-zipformer-korean-2024-06-16/tree/main))의 크기는 PoC에서 확인한다.
   - 메인오더 PC의 CPU를 쓴다. 게임 FPS에 영향을 줄 수 있다 (P-4).
   - 게임 용어 정확도는 학습 데이터에 달려 있다. 핫워드 기능으로 보완할 수 있는지 확인이 필요하다.

## D-2 오디오 처리: AudioWorklet + Web Worker

1. **문제**: 마이크 소리를 16kHz 모노로 바꿔 인식기에 계속 넣어야 한다. 메인 스레드에서 하면 화면 작업 때문에 끊기고, 백그라운드 탭에서는 타이머가 느려진다.
2. **대안**: ScriptProcessorNode는 폐기 예정이고 메인 스레드에서 돈다. 메인 스레드에서 직접 처리하면 위 문제가 그대로 남는다.
3. **가능해지는 것**: 오디오 수집(AudioWorklet)과 인식(Web Worker)을 화면과 분리해 끊김 없이 돌린다.
4. **비용·한계**: 스레드 사이에 데이터를 넘기는 코드가 늘어난다. 백그라운드 탭에서 실제로 멈추지 않는지는 PoC P-1로 확인한다.

## D-3 실시간 서버: Cloudflare Workers + Durable Objects

1. **문제**: 방 하나의 모든 사람이 같은 순서로 같은 상태를 받아야 한다. 서버 비용은 0원이어야 한다.
2. **대안**
   - 일반 Node.js 서버(VPS): 항상 켜 두는 비용이 든다. 무료 호스팅은 잠들었다 깨는 데 시간이 걸린다.
   - Firebase·Supabase 실시간 기능: 가능하지만 명령 상태 규칙(슬롯 스택)을 서버에서 한곳에 모아 처리하기 어렵다. 클라이언트끼리 규칙을 맞춰야 한다.
   - WebRTC P2P: 30명 연결과 NAT 문제가 복잡하다.
3. **가능해지는 것**: 방 하나 = 객체 하나. 그 객체가 상태와 연결을 함께 가지므로 순서와 동시성 문제가 생기지 않는다. Hibernation API를 쓰면 조용할 때 비용이 들지 않는다.
4. **비용·한계**
   - Workers Free 플랜에서도 Durable Objects를 쓸 수 있다. 단, SQLite 기반 객체만 만들 수 있다 ([Cloudflare 변경 기록](https://developers.cloudflare.com/changelog/2025-04-07-durable-objects-free-tier)).
   - 무료 한도를 넘으면 그 종류의 요청이 실패한다. 요금이 청구되지는 않는다. 한도는 매일 00:00 UTC(한국 시각 오전 9시)에 초기화된다 ([가격 문서](https://developers.cloudflare.com/durable-objects/platform/pricing)).
   - 들어오는 WebSocket 메시지는 20건을 요청 1건으로 센다. 나가는 메시지와 프로토콜 ping은 세지 않는다 ([가격 문서](https://developers.cloudflare.com/durable-objects/platform/pricing)).
   - 실행 시간(duration)은 객체가 메모리에 있는 동안 청구된다. 메시지가 계속 들어오면 잠들지 못한다 ([WebSocket 모범 사례](https://developers.cloudflare.com/durable-objects/best-practices/websockets)).
   - 잠들면 메모리 상태가 사라진다. 상태를 바꿀 때마다 저장소에 써야 한다 (FR-F04-10).
   - Cloudflare에 묶인다. 다른 곳으로 옮기려면 방 서버를 다시 만들어야 한다. `room-core`를 순수 함수로 분리해 이 비용을 줄인다.

### 사용량 계산 (동맹전 1회: 30명, 1시간)

| 항목 | 계산 | 결과 |
|---|---|---|
| 앱 ping (15초 간격) | 30명 × 240회 | 7,200건 |
| 명령·파티 선택 등 | 넉넉히 | 800건 |
| 들어오는 메시지 합계 | | 8,000건 → 요청 400건 (20:1) |
| 연결·재연결 | 30명 × 3회 | 90건 |
| **요청 합계** | | **약 500건** |

일일 무료 요청 한도는 10만 건으로 보인다. 다만 이 수치는 미리보기 문서에서만 확인했으므로 공식 문서에서 다시 확인한다. 이 수치가 맞으면 동맹전 1회는 한도의 1% 미만이다.

**주의**: 앱 ping이 15초마다 30명에게서 들어오면 객체가 거의 잠들지 못해 1시간 내내 실행 시간이 쌓인다. 줄이는 방법:
- `setWebSocketAutoResponse`로 ping에 자동 응답한다. 객체를 깨우지 않는다.
- 이것으로도 실행 시간 무료 한도가 부족한지 공식 한도 수치로 계산한다. **[확인 필요]**

## D-4 메시지 검증: Zod

1. **문제**: 서버와 클라이언트가 같은 메시지 형식을 써야 한다. 사용자가 보낸 메시지와 가져온 사전 파일은 믿을 수 없다.
2. **대안**: TypeScript 타입만 쓰면 실행 중에 검증하지 못한다. 손으로 검증 코드를 쓰면 타입과 어긋난다.
3. **가능해지는 것**: 스키마 하나에서 타입과 실행 중 검증을 함께 얻는다. `packages/protocol`을 서버와 웹이 함께 쓴다.
4. **비용·한계**: 번들 크기가 조금 늘어난다. 메시지가 작고 적어서 검증 비용은 무시할 만하다.

## D-5 프론트엔드: React + Vite + TypeScript

1. **문제**: 메인오더 화면과 동맹원 화면 두 개, 상태에 따라 바뀌는 UI가 많다.
2. **대안**: Svelte나 Solid는 더 가볍지만, 기획자에게 익숙하지 않으면 학습 비용이 든다. 프레임워크 없이 만들면 화면 상태 관리가 금방 복잡해진다.
3. **가능해지는 것**: 익숙한 도구로 빠르게 만든다. Vite는 WASM과 Worker 번들을 기본으로 지원한다.
4. **비용·한계**: 동맹원 화면의 첫 로딩이 조금 무거워진다. 동맹원 화면에는 STT 코드를 넣지 않도록 코드를 나눈다.

## D-6 UI: Mantine + 직접 만든 HUD

1. **문제**: 메인오더 화면에는 폼, 버튼, 모달, 알림이 많다. 동맹원 HUD는 게임용 시각 언어가 필요하다.
2. **대안**: 모든 것을 직접 만들면 메인오더 화면 개발이 느려진다. HUD까지 컴포넌트 라이브러리로 만들면 "1초 판독"에 맞는 디자인을 하기 어렵다.
3. **가능해지는 것**: 메인오더 화면은 Mantine으로 빨리 만들고, HUD는 SVG와 SCSS Modules로 직접 만든다.
4. **비용·한계**: 스타일 방식이 두 가지가 된다. 동맹원 화면에 Mantine 전체가 실리지 않게 주의한다.

## D-7 상태 관리: Zustand

1. **문제**: WebSocket 이벤트는 React 바깥에서 도착한다. 이 이벤트로 여러 화면 조각을 갱신해야 한다.
2. **대안**: React Context만 쓰면 이벤트마다 넓은 범위가 다시 그려진다. Redux는 이 규모에 비해 무겁다.
3. **가능해지는 것**: 연결 코드가 React 밖에서 저장소를 갱신하고, 화면 조각은 필요한 값만 구독한다.
4. **비용·한계**: 의존성이 하나 늘어난다. 방 상태 계산은 서버의 `room-core`가 하므로, 클라이언트 저장소는 받은 상태를 담는 그릇으로만 쓴다.

## D-8 로컬 저장: IndexedDB

1. **문제**: 사전, 지난 파티 구성, 세션 요약을 서버 DB 없이 남겨야 한다. 모델 파일(수백 MB)도 저장해야 한다.
2. **대안**: localStorage는 용량이 작고 동기 방식이다. 모델 파일은 Cache Storage나 OPFS가 더 맞다.
3. **가능해지는 것**: 설정과 기록은 IndexedDB에, 모델 파일은 Cache Storage 또는 OPFS에 둔다.
4. **비용·한계**: 브라우저 저장소가 지워지면 데이터가 사라진다. 사전은 내보내기로 백업한다 (F09). 작은 래퍼(예: idb-keyval)면 충분하고 Dexie 같은 큰 라이브러리는 지금은 필요 없다.

## D-9 시각화: SVG + CSS (Canvas는 지금은 필요 없다)

1. **문제**: HUD에는 아이콘, 위치 막대, 애니메이션 몇 개가 있다.
2. **대안**: Canvas는 많은 요소를 매 프레임 그릴 때 유리하다. HUD 요소는 수십 개 이하라 그럴 일이 없다.
3. **가능해지는 것**: SVG는 크기를 바꿔도 선명하고, CSS 애니메이션과 "동작 줄이기" 설정을 그대로 쓸 수 있다.
4. **비용·한계**: Phase 3의 지도 시각화에서 요소가 많아지면 그때 Canvas를 다시 검토한다.

## D-10 배포: Cloudflare

1. **문제**: 정적 웹과 방 서버를 무료로 배포해야 한다.
2. **대안**: 웹은 Vercel·Netlify에, 서버는 Cloudflare에 두면 도메인과 CORS 설정이 늘어난다.
3. **가능해지는 것**: 같은 계정과 도메인에서 웹과 WebSocket을 함께 제공한다. Cloudflare Pages 대신 Worker의 정적 자산 기능으로 한 프로젝트에 묶는 방법도 PoC에서 비교한다.
4. **비용·한계**: 모델 파일(수백 MB)을 정적 자산으로 올릴 수 있는지 파일 크기 제한을 확인해야 한다. 안 되면 Hugging Face 등 외부 주소에서 받아 브라우저에 저장한다. **[확인 필요]**
